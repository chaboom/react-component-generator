# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 쓰는 **기본값(fallback)** 이다.
- 둘이 충돌하면 프로젝트 규칙을 따르고, 충돌하지 않는 부분은 이 파일을 따른다.

## 1. 적용 기준

### TDD를 반드시 적용하는 대상

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 에러 매핑)
- **유틸리티 / 순수 함수**
- **버그 수정** (재현 테스트를 먼저 작성하고 실패를 확인한 뒤 고친다)

### TDD가 불필요한 대상

- **타입 정의** (interface, type)
- **설정 파일** (tsconfig, vite config, eslint 등)
- **순수 UI** (로직 없는 마크업, 스타일, 레이아웃)
- **SQL** (스키마, 마이그레이션)

판단이 애매하면 **적용 대상으로 취급**한다. UI라도 분기·상태·이벤트 로직이 있으면 그 로직은 적용 대상이다.

## 2. RED - GREEN - REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. import 오류, 오타, 문법 오류, 잘못된 셋업으로 실패한 것은 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화는 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체를 실행해 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 리팩터링 중간중간 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작**한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 임시 파일, 별도 브랜치 보관, 눈으로 보며 다시 쓰기 모두 해당한다.
- 이미 쓴 코드를 보고 테스트를 끼워 맞추면 구현을 검증하는 게 아니라 구현을 베끼는 것이다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드가 가장 자주 깨진 채 방치된다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과하므로 아무것도 증명하지 못한다. 실패를 본 적 없는 테스트는 신뢰할 수 없다. |
| "시간이 없다" | 테스트 없는 코드의 디버깅과 회귀 수정이 더 오래 걸린다. 급할수록 RED-GREEN의 짧은 루프가 빠르다. |
| "삭제하면 낭비다" | 매몰 비용이다. 검증 안 된 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 테스트 주도로 다시 쓰면 더 빠르고 더 작게 나온다. |
| "프로토타입이다" | 프로토타입은 버려질 때만 프로토타입이다. 남을 코드면 TDD 대상이다. 정말 버릴 코드라면 먼저 사용자에게 "버릴 코드"임을 확인받고 저장소에 커밋하지 않는다. |
