# Commit

변경사항을 읽고, 의미 단위로 나누고, 한국어 커밋 메시지를 작성해 **승인 절차 없이 바로 커밋**한다.
승인을 생략하는 대신 묶음과 메시지 품질이 중요하다. 커밋 후에는 무엇을 만들었는지 반드시 보고한다.

## 절차

### 1. 변경사항 파악

아래를 병렬로 실행한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log -n 8 --oneline
```

- `git log`는 이 저장소의 실제 메시지 스타일(scope 사용 여부 등)을 맞추기 위해 본다.
- untracked 파일은 `git diff`에 나오지 않으므로 `git status`로 확인하고, 필요하면 내용을 읽어 성격을 파악한다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

### 2. 민감 파일·불필요 파일 점검

`.env`, API 키, 자격 증명, `node_modules`, 빌드 산출물, 큰 바이너리가 포함돼 있으면 커밋 대상에서 빼고 사용자에게 알린다. 한 번 커밋되면 히스토리에서 지우기 어렵기 때문이다.

### 3. 논리적 단위로 분류

한 커밋은 한 가지 목적만 담는다. 아래 기준으로 묶는다.

- 목적이 다르면 분리한다. (기능 추가 + 무관한 설정 변경 + 리팩터링은 각각 별도 커밋)
- 같은 목적에 속한 코드·테스트·스타일은 함께 묶는다.
- 파일 하나 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p` 대신 사용자에게 분리 여부를 물어본다. (비대화형 환경에서 `-p`는 쓸 수 없다)
- 변경이 작고 목적이 하나면 억지로 나누지 않고 한 커밋으로 둔다.

### 4. 커밋 메시지 작성

형식:

```
<type>(<scope>): <요약>

<본문 - 필요할 때만>
```

**type**

| type | 용도 |
|------|------|
| feat | 사용자에게 보이는 기능 추가·개선 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 스킬, 빌드 등 잡무 |
| docs | 문서 |
| test | 테스트 추가·수정 |
| style | 포맷팅 등 코드 의미 없는 변경 (UI 디자인 변경은 feat) |

**작성 규칙**

- 요약은 한국어, 50자 안팎, 마침표 없이 "무엇을 했는지"를 쓴다. (예: `feat: 레트로 데스크톱 테마로 UI 전면 개편`)
- scope는 `git log`에서 이미 쓰고 있을 때만 붙인다. (예: `chore(skills): ...`) 쓰지 않는 저장소에 새로 도입하지 않는다.
- 본문은 "왜"가 diff만으로 드러나지 않을 때만 짧게 쓴다. 변경 파일 나열은 하지 않는다.
- 시스템 지침에 커밋 attribution(Co-Authored-By 등)이 있으면 메시지 맨 끝에 그대로 붙인다.

### 5. 커밋 실행 (승인 없이 진행)

이 스킬은 승인을 따로 받지 않는다. 다만 아래 경우에는 멈추고 사용자에게 묻는다. 되돌리기 어렵거나 의도를 추측할 수 없는 상황이기 때문이다.

- 민감 파일 의심 항목이 있어 어떻게 처리할지 불분명할 때
- 한 파일 안에 서로 다른 목적의 변경이 섞여 분리 여부를 정해야 할 때
- main 브랜치에서 작업 중일 때(브랜치를 만들지 확인)



- 커밋마다 해당 파일만 이름을 지정해 `git add <files>` 한다. `git add -A`/`git add .`는 다른 단위나 민감 파일을 끌고 들어올 수 있어 쓰지 않는다.
- 메시지는 heredoc으로 전달해 한글·줄바꿈이 깨지지 않게 한다.

```bash
git commit -m "$(cat <<'EOF'
feat: 요약

본문
EOF
)"
```

- hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 고친 뒤 새 커밋으로 만든다.
- 이미 만든 커밋을 `--amend` 하지 않는다. 사용자가 요청한 경우만 예외다.
- 마지막에 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인해 보고한다.

### 6. 마무리

push는 요청받았을 때만 한다. 승인 생략은 커밋에만 해당하며, push처럼 외부에 영향을 주는 동작에는 적용되지 않는다.

## 보고 형식

```
커밋 완료:
- a1b2c3d feat: ...
- e4f5g6h chore(skills): ...
남은 변경: 없음
```
